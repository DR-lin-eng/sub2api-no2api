# PR #180 多模态视频按次计费审查

审查范围固定为 [PR #180](https://github.com/DR-lin-eng/sub2api-no2api/pull/180)，原提交
`8405a81ba9270374a7d08faf404177d8aefb946c`，基线为 `22335a0ff4f4882531a3ff4f837e2d919d0c4946`。
本项目当前主线已包含 PR 169 的媒体工坊和视频冻结基础，本次只同步按次视频定价所需的增量，已覆盖或无关的媒体差异保持关闭。

## 采纳内容

- `video_balance_holds.billing_mode` 通过 256 号向前迁移记录冻结时的计费模式；旧冻结记录默认为空并继续按原来的按秒比例结算。
- `per_request` 视频在提交前要求分辨率命中 480p、720p 或 1080p 档位，支持 `720P`、`720`、`HD` 等标签别名；未指定或未知分辨率返回 `503 VIDEO_PRICE_NOT_CONFIGURED`，不再折算为 480p。
- 按次视频冻结、结算和用量记录都复用同一价格快照，结算不按实际生成时长比例折算；按秒视频保留原有时长口径。
- 管理端只在 multimodal 按次视频场景展示分辨率档位快捷项，避免把视频档位写入其他平台的普通按次定价。
- 缺价错误包含模型、请求分辨率、计费模式和已配置档位，便于管理员修正价格卡。

原 PR 的测试和 lint 失败由 `multimodal_video_billing_repro_test.go:761` 的 `svc.resolver :=` 非法赋值引起；本次测试以正确的字段赋值重写，并补充按次价格与结算比例回归。

## 升级、回退与性能边界

迁移只增加可空语义等价的 `billing_mode` 默认空字符串，重复执行安全。新节点读取旧记录时保留旧按秒结算行为；旧节点忽略新增列，回退不执行 Down SQL。完成所有节点升级后再启用按次视频价格配置，避免混合版本把未识别的计费模式当作旧视频模式。

请求路径只在已有分组模型索引或渠道缓存中读取计费模式，渠道查询为现有 O(1) 缓存查找；冻结记录把判断结果传入，避免冻结阶段重复回源。只有缺价错误才构造诊断信息并再次解析价格，不增加成功请求的数据库查询、队列或无界内存。

## 验证与关闭状态

Docker Go 1.26.10 定向测试通过：`application/service`、`infrastructure/repository`、`transport/http/handler`。前端生产构建的 `vue-tsc` 和 Vite 构建通过，相关管理端 21 项 Vitest 通过。临时将 Node 堆上限提高到 4 GiB 后完成完整 ARM64 Docker 镜像构建；仓库 Dockerfile 的 2 GiB 上限在本机 Docker Desktop 首次构建时 OOM，该资源限制不属于代码回归。

隔离 PostgreSQL 18、Redis 8 和构建镜像启动后 `/ready` 返回 200，迁移表记录 256，`billing_mode` 列存在；重复执行迁移安全，旧列投影和新列投影均可读取。未连接真实上游视频服务，也未部署生产节点。

PR #180 的同步差异已关闭。只有按次视频计费契约、冻结/结算行为或当前 owner 出现可复现回归时才重新审查，避免重复处理已覆盖差异。
