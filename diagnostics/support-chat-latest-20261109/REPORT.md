# 客服会话最新消息排序修复

基线：`76c848013dde0e26d077f86e3edf094a7e908704`，验证日期 2026-11-09。

## 复现与修改

上一轮覆盖了未读优先，但没有覆盖“多个会话多轮交流后全部已读”的完整链路。本次回归复现了以下问题：

- 后端按会话摘要 `last_message_at` 排序和返回时间；摘要停留在首次消息时间时会按旧时间分页。PostgreSQL 倒序默认还会把 NULL（空会话）排在有消息的会话前面。
- 前端使用 `updated_at` 代替缺失的消息时间，导致创建和标读时间影响排序。延迟/重放的旧消息、请求开始时的旧列表响应，也会覆盖已经收到的最新活动时间。

修复后，服务端从每个会话实际持久化的最后一条消息取得时间，并将同一值用于响应和分页排序，包含用户消息与客服回复；无需迁移旧数据。未读优先保持原有语义。同一状态中没有消息的会话排在后面。

前端仅以消息时间比较，旧事件不能降低最新时间；列表刷新只保留请求期间到达的更新，继续尊重服务端清理和搜索过滤。空会话显示已有的“暂无消息”提示。

修复前，新增的两项前端页面回归和两项数据库子用例稳定失败；修复后通过。数据库回归使用每页一条记录验证排序发生在分页前，也验证客服回复计入最新消息和已有未读优先行为。

真实 Docker HTTP 场景：先建立 A，再建立 B，最后回复 A 并全部标读，接口三页顺序为 A、B、空会话。刻意将摘要回写为各会话首次消息时间后，同一接口仍返回正确顺序与实际最新时间。

Playwright 浏览器访问修复镜像，验证客服侧全部已读时 A 排第一，整页刷新后保持不变。随后在真实输入框回复 B，B 立即变为第一；再次整页刷新仍为 B、A、空会话，所有会话均无客服未读标记。

## 查询成本与证据

现有 `(conversation_id, created_at, id)` 索引提供每个候选会话的一次反向索引定位，不扫描每个会话的完整历史。独立 PostgreSQL 的 1000 个会话、2 万条合成消息样本，`EXPLAIN ANALYZE` 显示使用该索引、执行约 1.157 ms；这不是生产性能保证。

[RESULTS.json](RESULTS.json) 保存镜像标识、源码摘要和测试结果；[records](records/) 保存压缩后的复现、测试、构建、SQL 和浏览器记录。本次测试使用 Go 1.26.10、Node 24、PostgreSQL 18、Redis 8；生产构建容器的 Node 堆上限设为 4096 MiB。

测试在独立本地环境执行，没有访问生产数据库。临时栈和合成数据已清理。
