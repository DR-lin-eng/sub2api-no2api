# 客服历史与实时同步排查

源码基线：`22335a0ff4f4882531a3ff4f837e2d919d0c4946`，叠加本次工作区修复。验证日期：2026-11-06。

## 结论和修复

在独立 Docker 环境中，没有复现“标记已读后数据库删除消息”。真实 HTTP、PostgreSQL 查询和浏览器验证均确认：双方发送、标记已读、重新登录、整页刷新，以及重启应用、PostgreSQL、Redis 后，消息仍可读取。

已稳定复现并修复两处前端问题：

- 用户端与管理员端刷新历史时直接替换消息列表，可能用旧响应覆盖请求期间收到的新消息或撤回状态。现在只将请求期间的更新合并到服务端历史中；已按服务端保留策略删除的旧消息仍会移除。
- socket 初次连接、重连成功后只更新在线图标，错过的消息需要等待轮询。现在两端连接成功后立即补拉 HTTP 历史。

四个页面回归用例在修复前均失败，修复后通过。这两处可以造成界面中消息消失或暂时收不到的现象；没有检查生产数据库，因此不能据此判断线上历史是否曾被删除，也不能认定它们是线上问题的唯一原因。多实例 Hub 的跨节点广播仍受现有文档中的边界限制。

## HTTP、数据库和真实浏览器验证

1. 在修复镜像上创建合成用户，用户和管理员分别发送消息，双方历史读取到相同 ID。
2. 双方标为已读，用户重新登录，历史仍存在；同一幂等键重试没有增加消息。
3. Playwright 使用两个独立浏览器登录用户端和管理员端，均显示已有历史与实时在线状态。
4. 通过用户输入框发送新消息，客服界面收到；通过客服输入框回复，用户界面收到。浏览器实际捕获到对应 WebSocket `message` 帧，分别对应消息 ID 5 和 4。
5. 停止应用，重启 PostgreSQL、Redis，再启动应用。两个浏览器自动重连并补拉 HTTP 历史，均显示 ID 1–5 共五条消息。
6. Docker 内 HTTP 接口重新读取相同五条消息；直接 SQL 查询确认消息总数与唯一 ID 数均为 5，双方未读数均为 0，重复幂等键组为 0。
7. 两个浏览器分别整页刷新，登录会话恢复后仍显示同样五条消息、双方正文和实时在线状态。

浏览器运行在宿主机，访问上述 Docker 镜像中的生产前端和后端。测试没有访问生产服务。
